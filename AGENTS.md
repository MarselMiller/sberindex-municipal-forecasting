# Правила работы с проектом СберИндекс

## Перед началом задачи
Прочитай README.md, docs/PROJECT_CONTEXT.md, docs/TASKS.md и конфигурацию текущего эксперимента.
Если файл отсутствует, сообщи об этом; не выдумывай его содержимое.
Проверь фактический статус рабочей папки. Не считай, что у тебя есть история браузерного чата.
Отвечай по-русски. Объясняй идею, изменения и результаты так, чтобы автор мог защитить работу.

## Границы задачи
Выполняй одну согласованную задачу за раз. Сначала укажи план и затрагиваемые файлы.
Не переписывай архитектуру и не обновляй весь набор зависимостей без обоснования.
Не меняй чужие или несвязанные незакоммиченные изменения; не удаляй их.
Перед установкой пакетов, скачиванием весов, полным обучением и сетевыми обращениями
согласуй действие с пользователем, если оно не было явно разрешено в текущей задаче.
Не выполняй push, публикацию, удаление данных или переписывание истории Git без явного разрешения.
Не читай и не передавай секреты, .env, ключи и пользовательские файлы вне проекта.
Применяй реальные ограничения доступа среды: этот файл и .gitignore не заменяют их.

## Исследовательские правила
Цель — месячное значение категории «Все категории» по МО; МО — муниципальные образования.
Не называй целевой показатель совокупным оборотом МО. Проверяй определение по документации данных.
MAE в исходной шкале обязательна, горизонты — 1, 3, 6, 12 календарных месяцев.
Изменения целевой переменной, выборки, временных разбиений и метрик — отдельное решение с записью причины.
Не допускай временной утечки: признаки, преобразования, обучающие метки, подбор параметров
и сигналы должны быть доступны на дату прогнозирования, с явно указанными допущениями.
Не подбирай модели по финальному тесту. Уже просмотренные результаты не называй новым слепым тестом.
Не обещай превосходство над Prophet до сопоставимого эксперимента.
Разделяй аномалию, обнаружение уже начавшегося изменения и предупреждение будущего шока.
Не выдавай ретроспективную сегментацию за раннее предупреждение.
Не выдумывай метрики, разметку, результаты запусков, даты доступности данных и источники.
Отдельно маркируй результаты: код подготовлен / команда выполнена / тесты пройдены /
получены метрики / сделан обоснованный исследовательский вывод.

## Эксперименты
Исходные данные и outputs/baseline_v1 не изменять.
Для нового опыта создавай новую YAML-конфигурацию и уникальный output_dir.
Сохраняй предсказания, метрики, покрытие, конфигурацию, seed, версии,
Git commit (когда Git настроен), признаки незакоммиченных изменений и команду запуска.
Сначала выполни минимальный разрешённый прогон; затем — согласованный полный эксперимент.
Сравнивай модели на одинаковых прогнозных случаях. Не скрывай ошибки, пропуски и fallback-прогнозы.
Не исправляй тесты лишь для получения зелёного результата; обосновывай изменения ожиданий.
Проверяй, что итоговые цифры и графики отчёта получены из сохранённых файлов результатов.

## Публикация
Не включай исходные и построчные производные данные, веса, .env и архивы в Git автоматически.
Проверь также выводы ноутбуков и вложения в reports: там может находиться исходная информация.
Состав публичной публикации и условия использования данных требуют отдельной проверки.
Для публичных проверок используй синтетические тестовые данные; не называй их реальными.

## В конце каждой задачи
Сообщи: какие файлы изменены; какие команды реально выполнены и их результат;
что проверено; что не проверено; ограничения; следующий конкретный шаг.
Обнови фактические статусы в docs/TASKS.md и устойчивые решения в docs/PROJECT_CONTEXT.md.
Не помечай задачу выполненной без прохождения её критериев готовности.
